# DESIGN.md

## 1. Структуры данных и алгоритмы

### Состояние игры и история попыток

Для хранения состояния игры используется обычный JavaScript-объект (тип `GameState` в `src/core/state.ts`), который содержит текущие настройки (`length`, `base`), сгенерированный секрет (`secret`), время старта (`startedAt`), время окончания (`finishedAt`), и массив истории попыток (`history`).

История попыток реализована как **иммутабельный массив** объектов вида `{ guess: string, bulls: number, cows: number }`.
При добавлении новой попытки (функция `addAttempt`) мы не мутируем старый массив через `push`, а создаем новый объект состояния и новый массив с помощью спред-оператора: `[...state.history, newEntry]`.
Это гарантирует, что старые состояния не меняются, что упрощает отладку, соответствует требованиям функционального программирования и позволяет легко отрисовать историю в UI, просто пробежавшись по массиву.

### Алгоритм `evaluateGuess`

Функция сравнивает секрет и попытку (обе строки приводятся к нижнему регистру для поддержки hex). Алгоритм работает в два прохода:

1. **Bulls (быки)**: с помощью `reduce` проходим по массиву символов попытки и сравниваем каждый символ с символом секрета на той же позиции. Считаем количество совпадений.
2. **Cows (коровы)**: создаем `Set` из символов секрета и `Set` из символов попытки (чтобы избежать дубликатов). Затем с помощью `filter` находим символы, которые есть в обоих множествах.
   Общее количество таких символов минус количество быков дает количество коров. Использование `Set` и методов массивов (`reduce`, `filter`) позволяет избежать ручных циклов со счетчиками и делает код более декларативным.

### Алгоритм `countPossibleSecrets`

Задача сводится к нахождению количества размещений без повторений (перестановок) \( P(n, k) = \frac{n!}{(n-k)!} \), где \( n \) — база системы счисления, \( k \) — длина секрета.
Реализовано **рекурсивно** на основе формулы:
`countPossibleSecrets(length, base) = base * countPossibleSecrets(length - 1, base - 1)`.
Базовые случаи: если `length === 0`, возвращаем `1`; если `length > base`, возвращаем `0` (нельзя выбрать больше уникальных цифр, чем есть в алфавите).
Результаты вычислений **мемоизируются** с помощью `Map`, где ключом является строка `${length},${base}`. Это предотвращает экспоненциальный рост вызовов при повторных вызовах функции (например, при открытии настроек).

## 2. Сложность (Big O)

- **`generateSecret(length, base, random)` — O(n)**, где n — длина секрета.
  _Обоснование:_ Внутри функции мы создаем массив доступных символов (алфавит) и в цикле (или рекурсивно) выбираем `length` элементов. Доступ к массиву и удаление элемента занимают O(1), поэтому общее время линейно зависит от длины генерируемого пароля. Память также O(n) для хранения строки результата.

- **`evaluateGuess(secret, guess)` — O(n)**, где n — длина секрета/попытки.
  _Обоснование:_ Функция делает несколько проходов по массивам длины n: один раз для подсчета быков (reduce), один раз для создания `Set` (занимает O(n) времени), и один раз для фильтрации общих символов (filter). В итоге сложность остается линейной. По памяти — O(n), так как мы создаем дополнительные массивы и `Set` размера n.

- **`isValidGuess(guess, length, base)` — O(n)**, где n — длина проверяемой строки.
  _Обоснование:_ Проверка длины занимает O(1). Приведение к нижнему регистру и создание массива символов — O(n). Проверка каждого символа через каррированный валидатор — O(1) на символ, итого O(n). Проверка на уникальность через создание `Set` — O(n). Следовательно, общее время выполнения линейно зависит от длины ввода.

- **`countPossibleSecrets(length, base)` — O(length)** (с мемоизацией).
  _Обоснование:_ Без мемоизации глубина рекурсии составляет `length` шагов. На каждом шаге выполняется O(1) операций. С мемоизацией повторные вызовы для тех же аргументов возвращаются за O(1) благодаря хэш-таблице (`Map`). Таким образом, время первого вызова — O(length), а последующих — O(1). По памяти — O(length) для стека вызовов и кэша.

## 3. Принципы чистого кода

В проекте применены следующие принципы из модуля Clean Code:

1. **Чистые функции (Pure Functions) и отсутствие побочных эффектов:**
   - Вся игровая логика в папке `src/core/` (например, `generateSecret.ts`, `evaluateGuess.ts`, `isValidGuess.ts`) не зависит от DOM, глобального состояния или времени.
   - Источник случайности в `generateSecret` передан параметром (`random = Math.random`), что делает функцию детерминированной при передаче мока в тестах.

2. **Иммутабельность (Immutability):**
   - В файле `src/core/state.ts` функция `addAttempt` не изменяет переданный объект `state`, а возвращает новый через спред-оператор (`...state`). Массив истории также создается заново (`[...state.history, entry]`), что исключает случайную мутацию старых данных.

3. **Функции высшего порядка (HOF):**
   - В `src/core/evaluateGuess.ts` для подсчета быков и коров используются методы `reduce`, `filter` и `map` вместо ручных циклов `for`. Это делает код более читаемым и выразительным.

4. **Каррирование (Currying):**
   - В `src/core/createDigitValidator.ts` реализована фабрика, которая принимает базу системы счисления и возвращает функцию-предикат `(char) => boolean`. Это позволяет переиспользовать валидатор как в функции `isValidGuess`, так и в UI (`src/ui/renderGame.ts`) для фильтрации ввода в реальном времени.

5. **Мемоизация (Memoization):**
   - В `src/core/countPossibleSecrets.ts` используется кэш (`Map`), чтобы избежать повторных рекурсивных вычислений при вызове функции с теми же аргументами (например, при переключении настроек туда-сюда).

6. **Семантическое именование и маленькие функции:**
   - Функции в `src/ui/` разбиты по своему назначению (`renderSettings`, `renderGame`, `renderRecords`), каждая отвечает только за отрисовку своего экрана. Имена переменных отражают их суть (`bulls`, `cows`, `history`, `entry`).

7. **Отказ от классов (Data-Driven & Functional):**
   - Вся игра построена на композиции функций и структур данных (объектов), без использования ООП-классов, что соответствует заданию.
